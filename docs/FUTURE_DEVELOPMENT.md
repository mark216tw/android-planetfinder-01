# 未來開發建議

本文件整理「找到星球」在 `1.2.0-prerelease` 之後的建議發展方向。排序原則是先提高計算正確性、實機可靠度與使用者信任，再擴充通知、天氣、星座或 AR 等功能。

## 發展原則

1. 正確性優先於功能數量。時間、位置、時區與方向錯誤會直接破壞尋星體驗。
2. 安全提示不可弱化。太陽相關畫面必須持續要求合格太陽濾鏡。
3. 離線核心應繼續可用。網路資料只能補充天候、光害或雲量，不應阻止基本天文計算。
4. 評級必須可解釋。使用者應能知道「推薦」或「困難」的主要原因。
5. 新功能應附帶測試、文件、無障礙與隱私影響評估。

## 優先級摘要

| 優先級 | 主題 | 目標 |
|---|---|---|
| P0 | 時區、感測器與實機驗證 | 確保不同城市與裝置上的時間、方向可靠 |
| P0 | 測試與錯誤處理 | 降低導覽、權限、旋轉與窄螢幕回歸 |
| P1 | 觀測規劃 | 加入天文事件、日期選擇、通知與分享 |
| P1 | 可觀測性品質 | 校準評分並加入環境條件的清楚區隔 |
| P2 | 天空內容 | 星座、亮星、深空天體與進階搜尋 |
| P2 | 視覺尋星 | 相機疊圖或 AR，但必須先完成方向可靠度驗證 |
| P2 | 正式發布 | 正式簽署、CI/CD、商店素材與隱私流程 |

## P0：正確性與可靠度

### 1. 依觀測位置處理時區

目前夜間時間窗與日期顯示主要使用裝置時區。使用者手動選擇東京、新加坡或其他遠端位置時，裝置時區可能與觀測地不同，造成「今晚」、日出、日落及日期歸屬不正確。

建議：

- 為預設城市保存 IANA 時區，例如 `Asia/Taipei`。
- 自訂經緯度允許使用者選擇時區，或在未連網時預設沿用裝置時區並清楚標示。
- 將 `ZoneId` 納入觀測位置與時間軸快取鍵。
- 所有日出、日落、夜間範圍與時間格式化統一使用觀測位置時區。
- 加入跨日、夏令時間、極晝與極夜測試。

完成標準：同一個遠端城市在不同裝置時區下，仍產生相同的當地觀測日期與升落時間。

### 2. 建立實機感測器測試矩陣

羅盤結果會受到硬體、Android 廠牌實作、螢幕旋轉與磁場環境影響，模擬器無法充分驗證。

建議測試至少涵蓋：

| 類別 | 驗證內容 |
|---|---|
| Rotation Vector 裝置 | 真北方向、四個主要方位、平滑效果 |
| 加速度計＋磁力計備援 | 方向、仰角、校準提示與穩定時間 |
| 缺少磁力計裝置 | 明確顯示不支援，不持續停在載入狀態 |
| 不同螢幕方向 | 直向、反向直向及支援時的橫向 |
| 磁場干擾 | 低精度提示、恢復高精度及避免誤震動 |
| 不同 Android 版本 | API 26、30、31、目前 Target SDK 附近版本 |

測試時應記錄手機型號、Android 版本、感測器類型、已知參考方向與觀察結果。

### 3. 驗證天文資料與邊界情境

建議以可信天文資料來源抽樣比對太陽、月球與行星的方位、仰角、升落時間及照明比例。

優先案例：

- 台北、赤道附近、高緯度北半球與南半球。
- 月出或日出接近午夜的日期。
- 水星與金星接近太陽時。
- 月球接近滿月、新月及地平線時。
- 星體兩日內無升落、極晝與極夜。
- 夏令時間開始與結束日期。

容許誤差應先明確定義，再將固定案例寫入單元測試，避免只檢查數值範圍。

### 4. 校準可觀測性評分

目前評級是規則式模型，適合作為起點，但門檻仍需要實際觀測與專家資料驗證。

建議：

- 將權重與門檻集中為可測試的設定，而不是散落在計算流程。
- 為太陽、月球、內行星、外行星及肉眼不可見行星定義不同基準。
- 區分「幾何可見」、「肉眼可見」與「需要器材」。
- 避免把有合格濾鏡才能觀測的太陽描述為一般「推薦」。
- 使用一組固定位置與日期建立 golden cases，人工確認評級與原因。
- 在 UI 清楚說明評級不包含天候、遮蔽物與人造光害。

## P0：測試與品質

### 5. 擴充 Compose 儀器測試

目前已有基本首頁、收藏與導覽測試，建議補充：

- 首頁、收藏、尋星與詳情頁的完整返回堆疊。
- 從詳情進入尋星，再使用 Android 返回鍵回到同一星體。
- 從動態 `finder/{bodyId}` 點選底部分頁。
- 時間軸點選、模擬時間更新與「回到現在」。
- 太陽與一般行星顯示不同時間軸文案。
- 定位權限允許、拒絕及永久拒絕流程。
- 空收藏、無感測器、地平線下與極夜狀態。
- 窄螢幕、大字體、淺色與深色主題。

建議加入 Compose screenshot 測試，特別保護羅盤刻度、長文字換行、系統列 Insets 與時間軸繪圖。

### 6. 改善可測試性

目前部分 UI 與狀態集中在大型 Compose 檔案。功能繼續增加後，維護成本會快速上升。

建議逐步拆分：

- `HomeScreen.kt`
- `FinderScreen.kt`
- `DetailScreen.kt`
- `ObservationTimeline.kt`
- `LocationDialog.kt`
- `Navigation.kt`

只在檔案已難以閱讀或元件需要獨立測試時拆分，避免為了架構形式建立過多抽象層。

可將時間來源、時區與 Astronomy Repository 透過小型介面注入 ViewModel，使即時更新與模擬時間測試不依賴系統時鐘。

### 7. 提升錯誤與載入狀態

建議將下列狀態明確呈現，而不是統一停留在載入畫面：

- 天文計算失敗。
- 定位逾時或所有 Provider 不可用。
- 保存位置資料損壞。
- 感測器缺失或長時間沒有事件。
- 通知權限或精確鬧鐘權限被拒絕。
- 網路補充資料不可用。

錯誤訊息應提供可執行的下一步，例如「改用手動位置」、「重新校準」或「繼續使用離線資料」。

## P1：觀測規劃功能

### 8. 日期選擇與多日預報

目前以即時與單一夜晚為主。建議加入日期選擇器，讓使用者規劃未來觀測。

可提供：

- 前後日期切換。
- 未來 7 天或 30 天的最佳觀測摘要。
- 每日最高仰角、最佳區間與主要限制原因。
- 使用者目前位置與收藏星體的快速篩選。
- 清楚顯示觀測地點、日期與時區。

多日資料應限制快取大小，並避免在主執行緒一次計算大量星體。

### 9. 天文事件

適合此 APP 的事件包括：

- 行星合、衝與大距。
- 月相與滿月、新月。
- 月球接近行星。
- 日出、日落、月出與月落。
- 行星達到夜間最高仰角。

事件卡片應直接連到對應星體、日期與模擬時間，減少使用者自行設定步驟。

### 10. 觀測提醒

允許使用者針對收藏星體或最佳區間建立本機通知。

實作前需考量：

- Android 13 以上通知權限。
- Doze、背景限制與重新開機後排程。
- 使用 WorkManager 或 AlarmManager 的適用差異。
- 時區、位置或日期改變後重新計算提醒。
- 避免重複通知及過多提醒。

第一版可只支援單次本機提醒，不需要帳號或雲端推播。

### 11. 分享觀測計畫

加入文字或圖片分享，可包含：

- 星體名稱。
- 觀測地點與當地日期。
- 最佳區間、方位與最高仰角。
- 評級與主要原因。
- 太陽安全提示。

分享前應讓使用者選擇是否隱藏精確經緯度，以避免不必要的位置隱私風險。

## P1：環境資料與評級

### 12. 天氣整合

雲量、能見度、濕度與降雨機率對實際觀測非常重要，但加入後會使 APP 需要網路權限與第三方服務。

建議採漸進方式：

- 保留純天文評級，另顯示「天氣條件」，不要混成無法解釋的單一分數。
- 顯示資料來源、更新時間與失效狀態。
- 天氣資料不可用時，核心天文功能仍正常運作。
- 在隱私文件列出送往服務商的位置精度與用途。
- API 金鑰只透過安全建置設定注入，不可提交到 Git。

### 13. 光害資訊

可加入 Bortle 級別或天空亮度作為觀測參考，但需要可靠資料來源與離線策略。

建議先提供使用者手動選擇環境：市中心、郊區、暗空地點。之後再評估地圖式光害資料，避免一開始引入大型圖資與複雜授權。

### 14. 地平線遮蔽

目前只使用幾何地平線。未來可提供簡易的使用者自訂遮蔽高度，例如東方有建築物遮蔽到 20°。

第一版可讓使用者為八個方位設定最低可見仰角。這比直接加入全球地形資料更容易離線運作，也更符合實際觀測位置。

## P2：內容擴充

### 15. 亮星與星座

建議先加入有限的亮星清單，再擴充星座：

- 優先收錄常用導航星與一等星。
- 顯示正式名稱、常見中文名稱、視星等與所屬星座。
- 沿用現有方位、仰角、時間軸與羅盤尋找流程。
- 星座線只作辨識輔助，不宣稱精密星圖用途。

資料集必須確認來源、版本與授權，並記錄在第三方套件文件。

### 16. 深空天體

可在亮星穩定後加入仙女座星系、獵戶座大星雲、昴宿星團等適合入門者的目標。

深空天體評級不能直接沿用行星規則，因為面亮度、視直徑、光害與器材口徑更重要。應建立獨立模型與器材建議。

### 17. 搜尋與篩選

當天體數量增加後，應加入：

- 中文、英文與別名搜尋。
- 目前在地平線上篩選。
- 肉眼、雙筒、望遠鏡器材篩選。
- 推薦程度與最佳時間排序。
- 收藏優先顯示。

在只有九個主要天體時不必過早加入複雜搜尋 UI。

## P2：AR 與視覺化

### 18. 相機疊圖或 AR

AR 很吸引人，但應在羅盤、姿態、螢幕旋轉與相機座標校準完成大量實機驗證後再開發。

風險包括：

- 磁力計誤差會讓標記明顯漂移。
- 相機視角與感測器座標需要精確校準。
- 低光環境下相機畫面品質有限。
- 相機權限與隱私說明增加。
- 太陽標記可能誘導使用者將相機或眼睛朝向太陽。

若實作，太陽模式應預設禁止相機尋星，或提供比其他目標更嚴格的安全流程。

### 19. 更完整的天空圖

可提供簡化全天圖，呈現地平線、方位、星體軌跡與目前視野。建議先做 2D 天空圓頂，不急於建立完整 3D 場景。

## 無障礙與國際化

### 20. 無障礙

建議：

- 為星體符號、愛心、羅盤及時間軸加入語意描述。
- 不只用顏色表達評級、暮光或感測器狀態。
- 支援 TalkBack 的焦點順序與按鈕名稱。
- 驗證系統字體放大至 200% 時不重疊。
- 確保淺色與深色主題對比符合 WCAG 建議。
- 提供關閉震動回饋的設定。

### 21. 多語言

目前大量字串直接位於 Kotlin 程式碼。正式國際化前應移至 Android string resources，並優先處理繁體中文與英文。

時間、日期、數字與角度格式應遵循 Locale；天體名稱則需維持可搜尋的別名對照。

## 效能與資料管理

### 22. 背景計算與快取

建議持續監測：

- 首次開啟至可操作畫面的時間。
- 九個天體時間軸的計算耗時。
- 多次切換模擬時間是否命中快取。
- 位置變更後舊快取是否正確失效。
- 長時間執行時的記憶體使用量。

若加入多日預報，可考慮使用有明確上限的 LRU 快取。除非資料需要跨啟動保存，否則不必急著導入資料庫。

### 23. 電量與感測器生命週期

尋星頁離開前景時應立即停止感測器。未來加入通知或背景工作時，要避免為了即時方向或位置持續喚醒裝置。

建議使用 Android Studio Energy Profiler 或 Battery Historian 抽樣驗證尋星 15 至 30 分鐘的耗電。

## 架構與維護

### 24. 狀態模型

隨著日期、天氣、事件與提醒增加，建議讓 ViewModel 狀態保持不可變，並區分：

- 使用者選擇：位置、日期、星體與收藏。
- 計算結果：天空位置、時間軸與評級。
- 暫時 UI 狀態：對話框、載入及錯誤訊息。

不應把高頻感測器資料全部提升到全 APP 狀態；方向與仰角可維持尋星頁生命週期內管理。

### 25. 依賴與升級

建議每個版本檢查：

- Android Gradle Plugin、Gradle、Kotlin 與 Compose BOM 相容性。
- Astronomy Engine 的變更與計算差異。
- Target SDK 新要求、背景限制與權限行為。
- 已知安全漏洞與棄用 API。

大型版本升級應獨立提交，避免和功能改動混在一起而難以定位回歸。

## 正式發布準備

### 26. CI/CD

建議 GitHub Actions 至少執行：

- 單元測試。
- Android Lint。
- Debug AndroidTest APK 編譯。
- Prerelease 或 release 組態建置。
- APK/AAB 雜湊與建置產物保存。

儀器測試可先使用受控模擬器執行；羅盤與磁力計仍需實機測試，不能只依賴 CI。

### 27. 正式簽署

目前 prerelease 使用 Debug 金鑰。正式發布前必須：

- 建立正式 upload key 與安全備份。
- 使用 GitHub Secrets 或受控建置環境注入簽署資料。
- 不將 keystore、密碼或 `local.properties` 提交到 Git。
- 決定是否使用 Google Play App Signing。
- 規劃 Debug 簽章測試版到正式簽章版本的安裝遷移方式。

### 28. 商店與政策

正式上架前需準備：

- 隱私權政策公開網址。
- Data safety 表單。
- 定位、通知與相機權限用途說明。
- 手機與平板截圖、圖示、簡介及完整說明。
- 太陽安全免責與使用警告。
- 支援信箱、版本紀錄與問題回報流程。

## 建議版本路線

### `1.2.x-prerelease`

- 修正實機回報、導覽、版面與羅盤問題。
- 完成觀測位置時區模型。
- 擴充 UI 與日期邊界測試。
- 校準可觀測性原因與門檻。

### `1.3.0-prerelease`

- 日期選擇與未來數日觀測摘要。
- 收藏星體的單次本機提醒。
- 天文事件列表與事件深層導覽。

### `1.4.0-prerelease`

- 可選的天氣條件整合。
- 手動光害等級與地平線遮蔽設定。
- 無障礙與字串資源重構。

### `2.0.0` 候選方向

- 正式簽署與商店發布流程。
- 穩定的多語言支援。
- 經過實機驗證的完整觀測規劃功能。
- 視需求加入亮星與星座；AR 不應是正式版的必要條件。

## 每個版本的完成條件

建議所有版本至少符合：

- 功能需求與限制已記錄。
- 新邏輯具有單元測試。
- 主要操作具有 Compose 測試或人工驗證紀錄。
- Lint、建置與適用測試通過。
- 至少在一台實機驗證定位、羅盤與返回導覽。
- README、使用指南、技術文件、變更紀錄與發行說明同步更新。
- APK 或 AAB 版本、大小、簽章與 SHA-256 已確認。
- 沒有金鑰、憑證、精確測試位置或其他敏感資料進入版本控制。

## 建議優先執行的下一步

若只選擇一個開發週期，建議依序完成：

1. 為 `ObserverLocation` 加入觀測時區並修正所有時間窗。
2. 建立至少三台不同感測器組合的實機測試紀錄。
3. 補齊導覽、時間軸、權限、大字體與窄螢幕測試。
4. 建立可觀測性 golden cases 並調整評分門檻。
5. 再開始日期選擇、多日預報與本機提醒。

這個順序能先降低錯誤時間與錯誤方向的核心風險，再增加真正能提升觀測成功率的新功能。
